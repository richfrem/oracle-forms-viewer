## 1. Concept: The Container Testbed as the Conformance Oracle

In reverse-engineering complex enterprise middleware, the primary failure mode is **speculative implementation**: guessing how Oracle Forms handles edge cases (trigger ordering, failure propagation, validation timing) and implementing an idealized model that diverges from real-world behavior.

Because this repository already maintains a certified, headless **Oracle Forms 14c and Database 23ai testbed** in Podman, we have access to the ultimate arbiter: **the genuine Oracle Forms runtime itself**.

We leverage this environment as our **Conformance Oracle**:
1. We construct small, targeted test forms.
2. Every trigger in the form logs its execution into an autonomous-transaction database trace table.
3. We execute a deterministic scenario of user actions on native Oracle Forms 14c (via FSAL) and capture the resulting trace as a **Golden Trace (`.json`)**.
4. We run the identical scenario through the Rust `oracle-forms-runtime` engine.
5. The test passes if and only if the Rust trigger firing sequence, system variables, and buffer mutations **match the Golden Trace**.

## 2. Trace Architecture & Database Schema

### 2.1 The Autonomous Trace Table (`ofw_trace`)

Because Forms triggers frequently fail, abort, or execute rollbacks, the trace logger MUST write outside the transaction boundary using `PRAGMA AUTONOMOUS_TRANSACTION`.

```sql
-- DDL for Conformance Trace Table
CREATE TABLE ofw_conformance_trace (
    trace_id        NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    session_id      VARCHAR2(64),
    step_seq        NUMBER,
    form_name       VARCHAR2(64),
    trigger_name    VARCHAR2(64),
    trigger_level   VARCHAR2(16),  -- 'FORM', 'BLOCK', 'ITEM'
    cursor_block    VARCHAR2(64),
    cursor_item     VARCHAR2(64),
    cursor_record   NUMBER,
    trigger_item    VARCHAR2(64),
    record_status   VARCHAR2(16),
    mode_name       VARCHAR2(16),
    custom_payload  VARCHAR2(255),
    logged_at       TIMESTAMP DEFAULT SYSTIMESTAMP
);

-- Autonomous Logging Procedure
CREATE OR REPLACE PROCEDURE ofw_log_trace(
    p_session_id    IN VARCHAR2,
    p_form          IN VARCHAR2,
    p_trigger       IN VARCHAR2,
    p_level         IN VARCHAR2,
    p_cursor_blk    IN VARCHAR2,
    p_cursor_itm    IN VARCHAR2,
    p_cursor_rec    IN NUMBER,
    p_trig_itm      IN VARCHAR2,
    p_rec_status    IN VARCHAR2,
    p_mode          IN VARCHAR2,
    p_payload       IN VARCHAR2 DEFAULT NULL
) IS
    PRAGMA AUTONOMOUS_TRANSACTION;
BEGIN
    INSERT INTO ofw_conformance_trace (
        session_id, step_seq, form_name, trigger_name, trigger_level,
        cursor_block, cursor_item, cursor_record, trigger_item,
        record_status, mode_name, custom_payload
    ) VALUES (
        p_session_id, ofw_trace_seq.NEXTVAL, p_form, p_trigger, p_level,
        p_cursor_blk, p_cursor_itm, p_cursor_rec, p_trig_itm,
        p_rec_status, p_mode, p_payload
    );
    COMMIT;
END;
/
```

## 3. Conformance Test Corpus (`samples/conformance/`)

A dedicated suite of minimal test forms (`.fmb` and Forms2XML `.xml`), each isolating a single architectural concern:

| Conformance Form | Test Area | Verified Invariants |
|---|---|---|
| `conf_01_startup.fmb` | **Startup Cascade** | Firing sequence on form launch: `PRE-FORM` $\to$ `PRE-BLOCK` $\to$ `PRE-RECORD` $\to$ `PRE-TEXT-ITEM` $\to$ `WHEN-NEW-FORM-INSTANCE` $\to$ `WHEN-NEW-BLOCK-INSTANCE` $\to$ `WHEN-NEW-RECORD-INSTANCE` $\to$ `WHEN-NEW-ITEM-INSTANCE`. |
| `conf_02_nav_valid.fmb` | **Navigation & Validation** | Tab/Click from Field A to Field B: `POST-TEXT-ITEM` $\to$ `WHEN-VALIDATE-ITEM` $\to$ `PRE-TEXT-ITEM` $\to$ `WHEN-NEW-ITEM-INSTANCE`. Verifies that `WHEN-VALIDATE-ITEM` only fires when the item is marked *dirty*. |
| `conf_03_query_cascade.fmb` | **Block Query Execution** | `PRE-QUERY` $\to$ Database SELECT $\to$ Per-record `POST-QUERY` $\to$ `WHEN-CLEAR-BLOCK` $\to$ `WHEN-NEW-RECORD-INSTANCE`. Verifies `:SYSTEM.LAST_QUERY` formatting. |
| `conf_04_master_detail.fmb` | **Master-Detail Coordination** | Relation `RelationInfo`: `ON-POPULATE-DETAILS`, automatic detail query, coordination modes (`Immediate`, `Deferred`, `Auto-Query`). |
| `conf_05_key_override.fmb` | **`KEY-*` Interception** | `KEY-NEXT-ITEM` and `KEY-EXEQRY` intercepting default actions; `DO_KEY('...')` invocation. |
| `conf_06_failure_abort.fmb` | **Failure Propagation** | `RAISE FORM_TRIGGER_FAILURE` in validation vs navigation triggers; verification that cursor remains locked in source item. |
| `conf_07_exec_hierarchy.fmb` | **Execution Hierarchy** | Item-level and Block-level `WHEN-VALIDATE-ITEM` with `Override`, `Before`, and `After` properties. |
| `conf_08_commit_pipeline.fmb` | **Commit Transaction Lifecycle** | `KEY-COMMIT` $\to$ `PRE-COMMIT` $\to$ Per-record (`PRE-INSERT`/`ON-INSERT`/`POST-INSERT`) $\to$ `POST-FORMS-COMMIT` $\to$ Savepoint rollback on error. |

## 4. Scripted Scenarios & Golden Trace Format

### 4.1 Scenario Specification (`.scenario.json`)

Scenarios describe user actions in an engine-agnostic schema:

```json
{
  "scenario": "test_tab_navigation_and_validation",
  "module": "conf_02_nav_valid.xml",
  "actions": [
    { "type": "SetFocus", "target": "BLOCK1.ITEM1" },
    { "type": "TypeInput", "target": "BLOCK1.ITEM1", "text": "INVALID_VALUE" },
    { "type": "NavigateNext" },
    { "type": "AssertFocus", "expected": "BLOCK1.ITEM1" },
    { "type": "TypeInput", "target": "BLOCK1.ITEM1", "text": "VALID_VALUE" },
    { "type": "NavigateNext" },
    { "type": "AssertFocus", "expected": "BLOCK1.ITEM2" }
  ]
}
```

### 4.2 Golden Trace Output (`.golden.json`)

The canonical output recorded from Oracle Forms 14c:

```json
{
  "scenario": "test_tab_navigation_and_validation",
  "oracle_version": "14.1.2.0.0",
  "trace": [
    { "seq": 1, "trigger": "WHEN-NEW-FORM-INSTANCE", "level": "FORM", "cursor": "BLOCK1.ITEM1" },
    { "seq": 2, "trigger": "POST-TEXT-ITEM", "level": "ITEM", "cursor": "BLOCK1.ITEM1" },
    { "seq": 3, "trigger": "WHEN-VALIDATE-ITEM", "level": "ITEM", "cursor": "BLOCK1.ITEM1", "status": "FAILED" },
    { "seq": 4, "trigger": "POST-TEXT-ITEM", "level": "ITEM", "cursor": "BLOCK1.ITEM1" },
    { "seq": 5, "trigger": "WHEN-VALIDATE-ITEM", "level": "ITEM", "cursor": "BLOCK1.ITEM1", "status": "SUCCESS" },
    { "seq": 6, "trigger": "PRE-TEXT-ITEM", "level": "ITEM", "cursor": "BLOCK1.ITEM2" },
    { "seq": 7, "trigger": "WHEN-NEW-ITEM-INSTANCE", "level": "ITEM", "cursor": "BLOCK1.ITEM2" }
  ]
}
```

## 5. Verification Gates by Phase

Every phased milestone must pass its associated conformance suite:

- **Phase B Gate (Runtime Spine)**:
  - Passes `conf_01_startup` and `conf_02_nav_valid` (stub execution verifying trigger resolution and event dispatch ordering).
- **Phase D Gate (Interpreter & Built-ins)**:
  - Passes `conf_03_query_cascade`, `conf_05_key_override`, `conf_06_failure_abort`, and `conf_07_exec_hierarchy` with exact golden trace parity.
- **Phase E Gate (Commit & CRUD Pipeline)**:
  - Passes `conf_04_master_detail` and `conf_08_commit_pipeline` with complete database state and rollback verification.

## 6. Continuous Integration (CI) Strategy

1. **Lightweight Fast CI (PR Gate)**:
   - Evaluates all conformance scenarios headlessly using the `SqliteDriver` or `MockDriver` in < 5 seconds.
2. **Oracle Conformance Matrix (Nightly / Opt-in)**:
   - Spawns the Podman `oracle23ai-lite` container, executes scenarios against the real database, and compares traces against `.golden.json`.
